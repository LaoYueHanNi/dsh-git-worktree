# DR: 移除工作树勾选开关，工作树动词按未开始会话门控进右键

Status: implemented

## Problem

工作树动词进入分支行右键菜单后（[分支行右键菜单](2026-09-13-branch-row-context-menu.md)），chip 旁的**「工作树」勾选开关**只剩一个职责：当模式位打开时，把"选分支"的语义从原地切换劫持成"建工作树"——而这个消歧在右键里已经由显式动词（签出 vs 创建工作树）完成了。模式位的剩余存在全是成本：一个需要重置的状态机（cwd 变化、会话启动、开关切换各一处）；"勾选后忘发消息"的知情默许边界（[勾选工作树即弹切出确认](2026-08-29-worktree-cutout-from-current-branch.md) 的一半篇幅在处理它）；菜单的换脸逻辑；以及一个两态控件占着的 composer 空间。

## Decision

勾选开关整体移除，工作树动词直接进右键、按**未开始会话**门控：

- **BranchChip**：`worktreeMode` 状态、勾选按钮、分隔线、`WorktreeCheck` 勾形组件及其 CSS 全部删除。chip 回归单按钮（分支选择器）。
- **BranchMenu**：`worktreeMode` prop 换成 `canWorktree`（owner 传 `session.blank && !inLinkedWorktree`）。分支行在六动词集内**追加**两个工作树动词，位置在新建并检出之后——「创建工作树」（非当前行；owner 的 `onWorktree` 直弹 reuse/新建/远程孪生确认，不走 `onSelect`——那条路是原地签出）与「新建分支并创建工作树」（含当前行——切出正是隔离动作）。已开始的会话两个动词都隐藏（目录已固定，隔离无从谈起），与「工作树」跳转分组（`canAdopt`）同一门控。
- **onSelect 回归单一语义**：选分支 = 原地签出（免确认、keep-open），不再有模式位分流；工作树创建只从右键动词发起。会话启动时清弹窗的 effect 保留（右键切出确认仍可能在会话启动时悬空）。
- 切出弹窗（手动输入新分支名，见 [切出弹窗的新分支名由用户手动输入](2026-09-14-cutout-branch-name-manual-input.md)）与 reuse/新建/远程孪生确认（`ConfirmState.worktree`）原样复用，只是入口从"勾选/选分支"统一为右键动词。

## Alternatives considered

- **保留勾选、右键也加工作树动词**——同一个动作（从该分支建工作树）两条入口、两套门控（模式位 vs blank），模式位打开时菜单还要决定"两套都显示还是换脸"，复杂度只增不减。放弃。
- **工作树动词已开始会话也显示**——目录身份已固定，动词必败或产生误导；与「工作树」分组随 `session.blank` 隐藏的既有口径一致。放弃。
- **开关改为"新建工作树"按钮**（点击直达当前分支切出弹窗）——仍占 composer 空间，而右键当前分支行的「新建分支并创建工作树」一步可达同一弹窗。放弃。

## Consequences

- 得：模式位状态机、"知情默许"边界、菜单换脸逻辑全部消失；composer 少一个控件；工作树创建的入口、门控（blank）、弹窗与签出/删除共享同一套右键机制，交互面一句话可述——未开始的会话里右键什么都能做，开始了就只剩原地动作。
- 代价：键盘/触屏用户失去勾选这条工作树创建路径（Enter 选分支现在永远=签出）——触屏本就无右键，叠加此改动后触屏完全无法创建工作树，只能靠开始会话前的终端；"勾选即弹窗"的主动引导消失，创建入口回到探索型（右键才发现）。
- 边界：`POST /worktree` 协议、`cutoutBranchName` 后缀巡检、reuse 语义全部不变；`canAdopt`（工作树分组）与 `canWorktree`（工作树动词）同源同值（`session.blank` 与 `!inLinkedWorktree` 的合取），未合并为一个 prop——语义不同（跳转分组 vs 创建动词），留 namespaced 两个 prop 表达各自意图。
