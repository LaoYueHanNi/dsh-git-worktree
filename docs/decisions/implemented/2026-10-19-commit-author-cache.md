# DR: 作者下拉缓存全部分支作者

Status: implemented

## Problem

作者下拉只从已经加载的 100 条提交里取名字。它是查找项，用户打开“全部作者”时会以为分支上只有这几个人。每次打开图谱都走一遍全历史又太贵。

## Decision

本记录部分取代[从分支菜单原位展开提交图谱](2026-10-18-branch-commit-graph.md)里作者名单的来源。文本搜索、列表筛选和分页不变：下拉可以列出尚未加载的作者，选中后仍只过滤已加载提交；名单里有、当前页没有的作者显示无匹配，继续加载后才会出现。

宿主增加只读 POST `/authors`。它接受与历史相同的显式分支或 HEAD，并使用历史响应里的 tip。用 `git log -z --format=%an` 收集该 tip 可达的全部作者名（与提交行的 `%an` 相同），去掉空名，按 `localeCompare` 排序。不限制条数，不读正文和补丁。

结果按仓库路径加 tip 放在宿主进程内存里，最多 32 条，超出丢掉最久未用的。同一次 tip 的并发请求共用一个进行中的扫描。扫描失败不写入缓存，重试会再走 Git。未出生的分支返回空名单，不扫描。

同一 tip 的提交作者不会变，所以平常命中缓存。分支信息更新时这份缓存作废：分支列表里的当前分支、领先/落后或上游发生变化，以及抓取、更新、推送结束（远程引用可能前进，但列表里看不出提交号）。作废丢掉该仓库的全部名单，并让已经出发的扫描不能再写回。图谱刷新按钮同样作废并重新读历史。作废之后的历史请求带 `freshAuthors`，宿主先丢掉该仓库的缓存再读；随后的作者请求按新的 tip 重新扫描。tip 没变时也会重扫一次，避免浅克隆补历史或引用被替换后仍拿旧名单。

页面里另有一份同样上限的内存缓存，失效规则与宿主一致。图谱拿到 tip 后先读这份缓存，命中则下拉立即是全量名单；未命中时下拉暂时用已加载提交里的作者，请求返回后再换成全量并写入缓存。写回时核对请求开始时的代次，代次已经增加则丢弃迟到的响应。切换分支或刷新会丢掉过期请求。

## Alternatives considered

**继续只列已加载作者**：下拉和当前页一致，但查找项会把后面的作者藏起来，用户无法知道分支上还有谁。

**把作者名单附在每一页历史上，打开时就全量扫描**：首屏要等完整遍历结束，大仓库打开变慢。拆成单独请求后，提交列表先出来，名单随后补全；再次打开同一 tip 不再扫描。

**选中作者后改走 `git log --author`**：能直接列出该作者的提交，但那是另一条列表，不再是当前分支分页里的筛选。本次只补齐下拉名单。

## Consequences

分支信息没有变化时，同一 tip 再次打开图谱不会重扫作者。抓取、更新、推送，或领先/落后、上游、当前分支发生变化时，会重扫一次；图谱上的刷新也会。第一次打开仍要遍历该分支可达提交，只取名字，大仓库会多一次 Git 日志；失败时下拉退回已加载作者。缓存最多各留 32 个 tip，更早的分支会再扫一次。选中尚未加载到的作者时，列表仍是无匹配，直到继续加载把他们的提交带进来。文本搜索仍然只覆盖已加载提交。没有上游的分支若只是新增提交、领先数没有变化，名单要等图谱刷新或下一次会改变分支列表的操作才更新。
