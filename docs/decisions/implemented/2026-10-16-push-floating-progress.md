# DR: 推送的悬浮进度：点推送后收起窗口，失败时带原因弹回

Status: implemented

## Problem

推送此前是审阅窗口里的一次性请求：按钮变"推送中…"，整个 `git push` 被 120 秒硬超时包住，没有任何进度。大量变更（几十 MB 的 pack、慢上行）下有三个后果：

- **超时误杀**：一次正常但较慢的上传在 120 秒被杀。更糟的是推送与拉取不同——超时**不能证明远端没有收到**，用户面对的是"到底推上去没有"。
- **黑盒**：传输期间既看不到阶段、计数、速度，也无法取消。
- **窗口被锁**：审阅窗口是模态的，且切换会话目录会卸载它；一次十几分钟的传输里，用户什么也做不了。

提取与更新已经有了悬浮进度卡片（[DR: 提取与更新的实时进度](2026-10-16-fetch-update-live-progress.md)），推送是同类的长传输，却成了最后一个黑盒。用户明确选择让推送走同一套悬浮卡片：点推送后窗口立即关闭，进度在卡片里，失败时再弹回窗口。

## Decision

### 宿主：`/push` 也是流式路由

- `POST /push` 改为 NDJSON 流（`streamPostRoute`），帧格式、"HTTP 恒 200、结果在 `done` 帧"、"断开连接即取消（499）"与提取/更新完全一致。
- live 路径给 `git push` 追加 `--progress`：计数（`Enumerating`/`Counting`/`Compressing`/`Writing objects: N% (a/b), 大小 | 速度`）在 stderr，`--porcelain` 的 ref 行在 stdout，两路合并后交给同一个 `progress.ts` 读取器。git 2.45 实测，慢上行时会在 `Writing objects` 阶段持续刷新百分比与速度。
- 约束由"120 秒总时限"改为 **5 分钟无任何输出即杀**加调用方的 `signal`；不设总时长。非 live 调用（不传 `live`）仍保持原来的 120 秒总时限，行为不变。错误文本去掉计数重绘与 `--progress` 带出的传输闲话（`stripProgress`：`Enumerating objects: N, done.`、`Delta compression using up to N threads`、`Total N (delta …)` 摘要），只留拒绝原因与 porcelain 行。展示时，凡是 `git <参数> failed (exit N):` 开头的文本都先去掉这句命令行再放进错误框，包括窗口叫不出名字的失败；不是 git 失败的原文（例如「远程未配置」）保持原样。命令行必须去掉：实机里本地 `pre-push` 钩子整条 `git -c remote.<名>.mirror=false push …` 占满短错误框，钩子自己的那句落在后面。这类失败单独成类 `hook`，中文说明是「本地的 pre-push 钩子拒绝了这次推送」，下面只留钩子自己的句子；`error: failed to push some refs to …` 在还有别的行时不显示。不归入 `refused`，那句中文说的是服务端钩子。闲话同样必须去掉：被服务端钩子拒绝的推送曾以四行闲话开头，真正说明原因的 `remote:` 行落在折叠线以下。
- **进度行的识别收紧**：合并 stdout 之后，porcelain 行（如 `*\trefs/heads/feat/50%-done:…`）与 git 的提示行会流经读取器；`NN%` 必须出现在"阶段名: NN%"（可带 `remote: ` 前缀）的行首才算进度，否则含 `%` 的分支名会被当成进度条。
- 取消 = 杀整棵进程树，路由答 499。远端只在**整包到齐后**才移动引用，所以被杀的推送不改变远端；极端窗口（远端已接收、本地 tracking ref 尚未更新时被杀）由随后的 `refresh` 校正。

### 前端：窗口交出推送，失败再弹回

- 点"推送"：`PushDialog.onPush` 把请求交给 `BranchChip` 后**立刻 resolve**，由所有者关闭窗口；推送本身进入作业仓库（`runSyncJob(cwd, 'push', …, { branch, remote })`），与提取/更新共享单飞、悬浮卡片和"同目录其它 git 动作等待"。卡片标题"正在推送 <分支> · <远程>"，其余同提取：git 原话、进度条、× 取消。
- **失败 = 弹回**：作业仓库新增按目录登记的失败记录（`recordPushFailure` / `takePushFailure`，只保留最新一条，取走即删）。dock 在挂载时和作业变更时取走本目录的失败，重新打开推送窗口并传入 `resume`（分支、远程、目标、标记范围、错误原文）。窗口据此初始化：原因已显示；远程/目标/标记恢复到失败时的选择（该远程已被移除则退回规划的默认目的地，原因仍在）；目的地未变时沿用本地快照；其余沿用"失败后重读远程预览"。用户在别的会话时失败的推送也不会丢——回到原会话，dock 挂载即取走并弹回。
- **强制推送不恢复**：强推是每次点击时的有意选择，失败后窗口默默带回会让下一次点击变成强推。`resume` 里没有 force，重试强推需再次明确选择。
- **取消不是失败**：toast"已取消推送"，不弹回窗口，不登记失败。用户关闭弹回的窗口即忘掉该失败，不会再次弹出。
- 推送完成后 `refresh()` 再提示成功（命名来源与目标）；期间若用户已切到别的目录，只登记失败/不提示，不回填新目录的事实。

## Alternatives considered

- **窗口保持打开，在窗内加进度条**——窗口是模态的，且切目录会卸载它，传输期间用户仍然什么都做不了；与提取/更新已确认的"不影响继续使用"冲突。放弃（用户明确选了卡片方案）。
- **只把 120 秒放宽或去掉，不做进度**——解决误杀，但黑盒与不可取消仍在，而"推上去没有"的不确定感才是核心。放弃。
- **点推送即关窗，失败只弹 toast**——被拒绝、lease 过期、认证失败恰是最常需要调整远程/目标/标记后重试的场景，让用户重新开窗、重选一遍体验差；失败还带着窗口已经会解释的原因分类。放弃，改为带原因与选择弹回。
- **弹回时只带错误文本，不恢复远程/目标/标记**——重试者要重做刚做过的选择，且更容易推到别处。放弃。
- **把 force 一并恢复**——见上，强推必须是明确的当次选择。放弃。
- **为推送另起一套进度/取消通道，或给 `/push` 加轮询**——宿主路由与前端作业仓库已经为提取/更新建好，推送只是第三种 `SyncKind`；新通道只增加协议面。放弃，复用。
- **失败登记放在 dock 组件状态里**——会话切换时 dock 卸载，失败会丢。放弃，用与作业同级的模块级登记。

## Consequences

- 代价：`/push` 的路由形态变了（NDJSON 流），**宿主进程需重启后才有进度**；新客户端对接旧宿主、或旧客户端对接新宿主，都会因整块 JSON 回退为无进度（旧宿主下依然窗口先关、失败照常弹回，只是还有 120 秒限制）；`PushDialog` 多一个 `resume` 属性，dock 多一个失败登记订阅；推送期间同目录其它 git 动作等待，与提取/更新一致。
- 所得：大量变更的推送不再被 120 秒误杀；传输期间看到 git 原话的阶段、计数、速度，可随时取消，页面可继续使用、切会话后卡片仍在；失败时回到原窗口，带着原因和原来的选择，一次点击即可重试。
- 边界：5 分钟没有任何输出仍会被杀（卡死的连接不应无限占用），静默超过 5 分钟的 `pre-push` 钩子同理——钩子在传输前运行，输出任何字节即重新计时；多引用更新不保证原子性的既有事实不变，失败后仍会刷新状态。
