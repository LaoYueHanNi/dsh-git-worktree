# DR: 提取与更新的实时进度：流式路由、逐远程拉取与悬浮进度卡片

Status: implemented

## Problem

提取（fetch）与更新（fetch + 快进）原先是一次性的 JSON 请求：整个过程被 executor 的 20 秒硬超时包住，且前端只有一个按钮上的透明度脉冲。大仓库或慢网络下有两个后果：

- **超时误杀**：一次正常但较慢的传输（几十 MB、跨境链路）在 20 秒被杀，用户只能看到失败 toast，而 git 已经传了大半。
- **黑盒**：传输期间没有任何信息，用户无法区分"慢"和"卡死"，也没有办法取消。IDEA 在同一场景下有后台任务卡片：阶段文字、百分比、速度、取消按钮，且不挡住继续操作。

## Decision

### 宿主：流式路由，进度只转述 git 自己的输出

- `POST /fetch`、`POST /update` 改为 **NDJSON 流**（`application/x-ndjson`）：立即回 200，之后每行一个 `SyncFrame`——`progress {text, percent?, remote?}`、`merge`（拉取结束、开始快进）、最后一行必为 `done {status, body}`，其内容就是原先一次性应答的状态码与 body——处理器自己的结果（含 400 校验失败、499 取消、500 git 失败）一律走 `done` 帧，HTTP 状态恒为 200；只有流开始之前的请求体级失败（过大、非法 JSON）仍是普通 JSON 的 400。
- 进度来自 `git fetch <remote> --prune --progress` 的 stderr，由 `progress.ts` 的纯函数读取器解析：按 `\r`/`\n` 切行、去掉 `ESC[K` 等终端控制序列、取行内 `NN%`；**文案是 git 原话（不本地化）、百分比是 git 算好的百分比（不做二次计算）**，同阶段的重绘按 150 ms 节流，新阶段立即放行，结束时刷出最后一条被节流的观测。
- **逐个远程自己拉取，而不是 `fetch --all --progress`**：live 路径先 `git remote` 取全部远程、`git config --bool --get-regexp ^remote\..+\.skipfetchall$` 剔除被标记跳过的（与 `--all` 一致），再对每个远程执行 `git fetch <remote> --prune --progress`，每个远程开始前先 `onRemote(name)` 让进度读取器给出 `Fetching <name>` 并给后续行打上远程名。与 `--all` 同语义：某个远程失败不阻止其余远程，全部跑完后合并各自的错误文本，以 `git fetch --all --prune failed (exit N): …` 抛出（错误文本已去掉进度重绘）。非 live 调用（新建 worktree 前的同步）仍是单条 `fetch --all --prune`，行为不变。
- **live 执行不再有 20 秒总时限**：live 路径走 `spawn` 流式读取，约束改为 **5 分钟无任何输出即杀**（`idleTimeoutMs`）加调用方的 `signal`；不设总时长，只要 git 还在出字节就让它跑。
- **取消 = 断开连接**：客户端 abort → 响应的 `close` 事件（不是 `req` 的，请求体读完后 `req` 的 close 不代表客户端走了）→ 处理器的 `signal` 中止 → 杀整棵进程树（Windows 上 `taskkill /T /F`，否则 ssh/https 传输子进程会残留）→ 路由答 499 `Cancelled`。更新在拉取结束、发出 `merge` 事件后**不可再取消**；拉取结束的瞬间若已收到取消，也不会再去快进用户的分支。

### 前端：与 dock 解耦的作业仓库 + 悬浮卡片

- `sync-job.ts` 是模块级作业仓库（不进 React 状态）：**每个目录单飞**、持有 abort 句柄、广播变更。dock 随会话切换卸载/重建，作业与卡片不受影响，回到原会话仍能看到进行中的卡片，也不会在其上再起一个 `git fetch`。
- `SyncProgress` 悬浮卡片 portal 到 `body`，卡片外区域 `pointer-events: none`，**不是模态**：用户可继续输入、浏览、切会话。内容 = 动作与远程名（"正在提取远程分支 · fork"、"正在更新 main"）、git 原话的阶段/计数/速度（第一行输出之前显示"正在连接远程…"）、进度条（有百分比 → 确定条；该阶段 git 给不出百分比 → 不确定扫光条）、右上角 × 取消。快进阶段显示"正在快进 <分支>…"，× 隐藏。`prefers-reduced-motion` 下去掉动画。
- 作业期间同一目录的其它 git 动作（切换、创建、推送、再次提取/更新等）经 `blocked()` 与菜单 `busy` 挡住——它们与拉取会争同一把 git 锁和同一组 refs。
- 取消的反馈是单独的 toast（"已取消提取"），不当失败处理；失败走原有错误提示。
- 客户端对"非流式"应答（请求体级 400，或尚未升级的旧宿主返回的整块 JSON）回退到一次性信封解析：功能可用，只是没有进度；流在 `done` 帧之前被切断按失败处理（`Connection closed before the operation finished`）。

## Alternatives considered

- **只把 20 秒超时调大/去掉，不做进度**——解决误杀，但黑盒与无法取消仍在；用户在"是否卡死"上的不确定感才是核心问题。放弃。
- **`git fetch --all --progress`，保持单进程**——在 git 2.45 上实测：多远程时 git 为每个远程起子进程，子进程拿不到 `--progress`，stderr 非终端时只会剩下 `Fetching <remote>` 一行，没有任何计数；而 fork 工作流（origin + fork）恰是本插件的典型用法。单远程时有计数，所以单测里的单远程用例曾掩盖了这个问题。放弃，改为逐个远程拉取。
- **`-c fetch.unpackLimit=1` 之类强制出计数**——会改变用户仓库的对象落盘方式（松散对象 vs 包）来换一个展示效果，属于借进度之名改存储行为。放弃；对象很少的小传输本来就瞬间完成，没有可展示的进度。
- **前端自行估算百分比/总量/剩余时间**——git 在 `Counting`/`Compressing` 等阶段并不给总量，估算的数字会骗人。放弃，只呈现 git 给出的百分比；给不出时用不确定条。
- **进度文案本地化/结构化重排**——git 原话（含 `708.01 KiB | 128.00 KiB/s`）与终端、IDEA 一致，用户已熟悉；翻译会引入解析脆弱性（git 自己随 locale 变文案）。放弃。
- **模态对话框（如推送审查窗）展示进度**——推送是用户要逐项确认的写操作，对话框合理；拉取是后台同步，挡住输入违背"不影响继续使用"。放弃，用悬浮卡片。
- **SSE / WebSocket / 轮询另开进度通道**——宿主路由是裸 Node `req/res`，POST + NDJSON 响应无需新协议或二次握手，且"断开连接即取消"自带语义；轮询还需要服务端保存作业状态。放弃。
- **快进阶段也允许取消**——快进是本地毫秒级操作，中途停下只会多出一个"到底动没动"的状态要解释。放弃，进入 `merge` 即隐藏 ×。
- **组件状态里存作业**——会话切换后 dock 重建会忘记作业并允许重复起 git。放弃，用模块级仓库。

## Consequences

- 代价：多远程时 live 路径多两次轻量 git 调用（`remote`、`config`）并逐个顺序拉取（`--all` 默认同样是顺序）；宿主多了一个路由形态（NDJSON）与进程树清理逻辑（Windows 专用的 `taskkill`）；前端多一个模块级仓库和一个 portal 卡片。已升级客户端对接旧宿主、或旧客户端对接新宿主，都会因"非流式/整块 JSON"而降级为无进度，不会失败——但新特性需重启宿主进程后才生效。
- 所得：大仓库/慢网络不再被 20 秒误杀；进度、速度、远程名一目了然且全是 git 原话；任何时候可取消，取消后无残留进程，已完成远程的引用保持更新、未完成的远程不被改动（git 在传输成功后才更新该远程的引用）；拉取期间不阻塞用户继续使用。
- 边界：无输出 5 分钟仍会被杀（卡死的连接不应无限占用）；单远程失败其余继续，合并报错；取消只在拉取阶段可用。
- 推送沿用同一套流式路由、作业仓库与悬浮卡片（第三种作业类型），见 [DR: 推送的悬浮进度](2026-10-16-push-floating-progress.md)。
