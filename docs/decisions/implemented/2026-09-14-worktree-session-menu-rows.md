# DR: 工作树会话展示什么——本目录分支 + 可跳的工作树

Status: implemented

## Problem

[工作树会话的菜单作用域三分](2026-08-31-worktree-session-menu-scope.md)给链接工作树会话定的是「置灰 + 拦截」：分支行照常展示，非当前分支置灰，动作被 owner 拦成一句 toast。这个方案自 2026-09-04 起因判据字段语义漂移而整体没跑起来（见[会话所在工作树的判据](2026-09-14-toplevel-and-main-facts.md)），判据修好后又收窄了一层（被拒绝的动词不再展示）。但收窄只是止痛：菜单里仍是一整片灰行，右键仍要点开一个只剩「复制分支名」的菜单，搜索框仍能筛出一些点了没用处的结果。用户的判断是——**既然都不能操作，展示它们本身就是噪音**：把「不能动」编码成「看得见」，成本落在每一处交互上。

于是第一版收敛把工作树会话的列表压成了**单行**：只有本目录检出的那个分支。这解决了噪音，但**收得过头**：工作树存在的意义就是在多个工作目录之间来回，而「跳到此工作树」恰好是这类会话里**唯一合法且最需要**的动作——它的实现是 `adoptWorktree`（注册目录 + 开一个新的空白会话），从不移动任何检出，因此与「目录 = 分支」这条底线毫无冲突。单行把工作树组连同噪音一起砍掉了，结果是在 `main-2` 里想切到 `main-wt1` 必须先回主检出会话，绕一圈。

用户的修正（本轮触发）：**工作树分组要展示出来，方便工作树之间切换**。

## Decision

**链接工作树会话的行集 = 本目录的分支 + 每一棵「其它」工作树（主检出在内）。**

- **本目录分支**（`kind: 'local'`，一行）：位置标记，带 HEAD 勾与 ahead/behind 箭头——就是 chip 上那个名字，落在行列表里做「你在这里」。
- **其它工作树**（`kind: 'worktree'`，每棵一行）：右键菜单就是既有的「跳到此工作树」（`adoptWorktree`）+「复制路径」，与主检出会话里的工作树行完全是同一套语义与同一个组头。空白与已启动会话都展示——跳转开着新会话，不影响当前这个。
- **排除会话自己所在的那棵，其余全收**，规则统一为「除你所在的那棵以外的每一棵工作树」：主检出会话里"你所在的那棵"就是主检出自身（于是 `w.main` 出局，与既有行为一致）；工作树会话里按**分支**排除（`w.branch === currentBranch`），**主检出因此留在列表里**——从工作树里看，主检出正是另一个要去的地方，而不是"原地"。detached 工作树没有分支名可标，一并排除。
- **其它分支一律不展示**：本地、远程分支仍然不在列表里。目录的身份就是它的分支，展示它们只能换来被拒绝的行——这条判断不变。
- 因此 **`canAdopt` 的门槛改为「主检出 blank 会话，或任意链接工作树会话」**；**已启动的主检出会话仍不提供该组**（那是 2026-08-31 的既有裁决，本次不动，也不因这次改写而顺带放开）。
- 与 `canWorktree` 是两个独立门槛：那条是**创建工作树**的写入动词，只在主检出的 blank 时刻；这条是**读+跳**的面板，工作树会话同样拥有。
- **锁定行机制保持删除**（`BranchRow.locked`、`.menuRowLocked`、`mainRepoOnly`、搜索 Enter 特例、右键动词门槛——它们的引入与退场见[工作树会话的菜单作用域三分](2026-08-31-worktree-session-menu-scope.md)第 2 点及其修正注记），不因这次回退而复活：展示出来的每一行都真的有动作。

## Alternatives considered

- **只留本目录分支一行**（本条的上一版形态）——收得过头：把工作树之间切换这一核心能力一起砍掉，用户必须绕回主检出会话。工作树是「多个工作目录」的设施，砍掉跳转等于承认它们之间没有关系。放弃。
- **保留「置灰 + 拦截」的全量展示**——原方案，噪音问题就是它逼出来的；本次否决理由不变：置灰行占着菜单绝大部分面积而唯一用途是「告知存在」，这份信息在主检出会话里免费可得。放弃。
- **展示工作树组，同时也展示其它分支（带灰）**——比原始方案稍窄，但灰行仍然存在，噪音只是缩小。灰的本质问题是「能看不能用」，而分支列表的「看」在工作树会话里没有增量价值（主检出可看）。放弃。
- **工作树组里包含本会话所在的那棵**（靠 HEAD 勾表示「你在这里」）——会让同一分支出现两次（本地组那行 + 工作树组那行），而 worktree 行的右键菜单只有 hop/copy，对「你所在的那棵」两个都不成立（跳回原地、复制自己路径意义有限）。排除它更干净：工作树组的含义就是「可以跳过去的地方」。放弃包含。
- **工作树会话里把主检出也排除**（只允许在工作树之间跳）——本轮实现中途采纳过，随即发现它常常等于没加：一个仓库最短的形态就是两棵工作树（主检出 + 你现在这棵），排除主检出后组里是空的。而且「回主检出」恰恰是工作树会话最常见的诉求之一——它是你创建下一个工作树、做分支写操作的地方。所以排除口径按「你所在的那棵」而不是「linked worktree」（`w.main` 是主检出会话侧的等价表达，两侧规则因此是同一条）。放弃排除主检出。
- **顺带让已启动的主检出会话也展示工作树组**——没有可达行为差异（hop 照样开新会话），但会推翻 2026-08-31 对 started 会话的裁决，而本轮没有任何用户诉求指向它。保持不动，留待有诉求时单独议。放弃。
- **工作树会话干脆不渲染 chip**——chip 是位置标记，且提取/更新两个工具挂在它旁边。放弃。
- **把跳转做成 chip 上的独立按钮**（不占菜单行）——多一个常驻控件去解决一个菜单里一行就够的事，且「跳到哪里」还要再选一次。放弃。

## Consequences

- 得：工作树会话在两步之内就能切到另一棵工作树，或跳回主检出（右键 → 跳到此工作树），这正是工作树设施的日常动作；菜单仍然干净（通常「本地分支」1 行 + 「工作树」N 行，没有灰行、没有被摘空的右键菜单）；`locked` 那套机制保持删除，行模型继续是「每一行都可执行」。
- 代价：`canAdopt` 的语义从「blank 才有」变宽成「主检出 blank 或链接工作树会话」，读 prop 文档才能知道 started 主检出为什么不在此列；工作树会话的 `rows` 形状（本目录分支 + 其它工作树）与主检出会话的（三分组）不同，且两侧的工作树过滤条件写法不同（一侧 `w.main`、一侧 `w.branch === currentBranch`）——它们表达的是同一条「除你所在的那棵以外」的规则，只能靠两份文档把它接上；本次没有恢复「一眼看全仓库分支」的能力，那是主检出会话的事。
- 边界：`adoptWorktree` 对**已注册为 workspace** 的工作树同样走 `workspaces.create` + `startSession`（既有行为，主检出会话的 hop 一直如此），若某天该调用对重复注册报错，两个入口会一起坏——不在本次改动范围内；detached 工作树与本目录分支缺失（`currentBranch` 为 `HEAD`）时行集退化为仅工作树组或空列表，属诚实形态；判定仍基于打开菜单时的 status 快照，终端里在别处增删工作树插件不感知。
