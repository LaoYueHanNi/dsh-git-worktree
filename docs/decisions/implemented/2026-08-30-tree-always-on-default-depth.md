# DR: 分支树常驻渲染，数量只决定默认展开深度

Status: implemented

## Problem

弹层优化时期引入的 `TREE_MIN_ROWS = 8` 是"平铺 vs 树形"的双模式开关：本地分支不足 8 个时整个列表平铺、折叠按钮禁用。实际使用中这造成两个问题：小仓库（分支 3–8 个、共享前缀）失去分组折叠能力，禁用态的折叠按钮看起来像坏了——维护者自己在 5 分支仓库里就误判为"按钮失效"。平铺与树形两套渲染路径（renderRow / renderTree）也让代码分叉。

## Decision

树形**常驻渲染**：`buildTree` 不再有分支数条件，`renderRow` 平铺路径删除，折叠按钮常显（无文件夹时禁用）。`TREE_MIN_ROWS = 8` 语义改为**默认展开深度阈值**：超过 8 个分支时默认只展开当前检出分支的祖先链（其余折叠，靠 locate/居中定位）；不超过 8 个时默认全部展开——少量分支没有可藏的东西，摊开反而好扫。打开菜单的重置逻辑通过 ref 读取最新 rows（effect 仍只依赖 `[open, currentBranch]`），会话中途的 refresh 不会重置用户手动折叠的文件夹。

## Alternatives considered

- **维持双模式**——就是被推翻的现状：小仓库无折叠、死按钮观感、双渲染路径分叉。
- **去掉阈值，一律只开当前链**——小仓库里唯一的 feature 文件夹默认关着，打开菜单看到的是一行文件夹头，扫视成本高于收益。放弃。
- **去掉阈值，一律全开**——大仓库（几十个分支）打开即整棵树摊开，"缩起来展示"的诉求落空，居中定位也只能在被淹没的列表里找当前行。放弃。
- **阈值改为 3**（上一版过渡方案）——仍然是双模式，只是挪了门槛，"少就不渲染树形"的模型本身被需求否定。

## Consequences

- 代价：`renderRow` 删除后单分支、双分支仓库也走 buildTree（纯内存前缀树，开销可忽略）；一两个无前缀分支的仓库会出现零文件夹的树（渲染等同平铺列表，仅少了平铺路径的代码）。
- 换来：折叠能力在任意规模可用，折叠按钮永远有真实作用；渲染路径合一（搜索态本就只有树形实现）。
- 边界：8 的阈值沿用了旧平铺门槛的数值，纯经验值；若实际体验失衡（比如 7 个分支默认全开太吵），只动这一个常量。
