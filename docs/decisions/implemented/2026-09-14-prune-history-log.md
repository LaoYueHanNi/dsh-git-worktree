# DR: 自动清理落清理记录（浏览器本地），设置卡片可查

Status: implemented

## Problem

自动清理的反馈只有一条一闪而过的 toast（"清理了 N 个"）：不报删了**哪些**目录，toast 消失后也无从追查。而 prune 的活跃度口径是纯会话的——"只在终端干活"的目录 activity=0、排在删除队列最前，这正是最需要事后核查的误判形态；当用户回头发现某个工作树没了，没有任何记录能告诉他"是哪一轮自动清理删的、当时删了哪些别的"。

## Decision

每轮自动清理（`pruneWorktrees`）执行完毕且**有内容**（removed/skippedDirty/failed 任一非空——空跑不入账，避免噪声）时，把运行记录落进 **localStorage**：

- **记录形状**：时间戳 + removed 数组（每项 path + 所属项目 + 分支——belonging 取自 `/worktrees-all` 的扫描结果，记录读作"哪个项目丢了哪个工作树"而非裸路径）+ skippedDirty + failed（解释"一轮什么都没删"的运行）。
- **容量**： newest-first，最多 20 轮，超出截尾——日志是近期活动轨迹，不是档案。
- **存储位置 = localStorage，刻意不进设置文档**：删除发生在本浏览器（ordering 依据的会话活动度也只在本浏览器可见），记录天然 per-browser；进设置文档则会被第二个浏览器同步到一份它没执行过的删除史。读写全 try/catch——隐私模式/配额下日志静默失效，清理本身不受影响（toast 已是第一反馈）。
- **展示**：设置卡片 autoPrune 开关之下新增「清理记录」区（仅开关打开时渲染，展开卡片即重读）：每轮一行相对时间 + "清理了 N 个：`repo/branch` · …"，skipped/failed 以次要色调附注；空日志显示占位。

## Alternatives considered

- **只改 toast 文案列出目录**——信息在弹出的几秒后依旧消失，排查发生在几分钟/几天后。放弃，toast 与记录共存。
- **记录进设置文档（随配置同步）**——删除史变成跨浏览器同步的状态：浏览器 B 会看到自己从未执行、也无法验证的删除记录；且日志写入会触发设置文档的保存语义（staged/dirty），语义错位。放弃。
- **host 侧持久化（storage root 下的日志文件）**——写入方在浏览器，还要新增一条日志追加路由；而记录的消费方（设置卡片）也在浏览器，host 落盘没有增加任何可及性。放弃。
- **连手动删除（侧栏/管理弹窗）一并记录**——手动删除是用户在确认弹窗里逐个点掉的，过程本身可见；自动清理才是"睡了一觉起来少了几块"的盲区。首期只记自动清理，手动删除暂不入账。

## Consequences

- 得：误判活动度后可追责到具体轮次与全部受害者；"这轮为什么什么都没删"（skippedDirty/failed 入账）也有了答案；实现是 30 行纯 localStorage 模块，零协议改动。
- 代价：记录 per-browser——换了浏览器/清了站点数据即消失（与"记录浏览器侧删除"的定位一致）；上限 20 轮，更早的历史不可考。
- 边界：`recordPruneRun` 对空跑不入账——"开关开着但一直没触发过删除"在记录里与"没开开关"不可区分（开关状态本身就在旁边的设置项上，不算信息损失）；`repoName/branch` 取自扫描时刻的快照，若扫描后目录被外部移动，记录里的归属可能过时。
