# DR: 工作树菜单行补齐上游落后超前指示并在试行后评估保留

Status: proposed

## Problem

在分支弹出菜单（`BranchMenu`）中，普通本地分支行会在右侧直观展示该分支相对于上游（upstream）的领先与落后计数箭头（如 `↑1`、`↓2`）。然而，当分支被工作树检出后，它会被分类移动到「工作树」分组行展示。

当前客户端在从后端 `RepoStatus` 组装工作树行数据模型（`BranchRow`）时，未将对应本地分支已计算完毕的 `ahead`/`behind` 计数带入工作树行对象；同时，工作树扁平行渲染器（`renderFlatLeaf`）也遗漏了调用 `renderArrows(row)`。这导致同一分支在未建树时可清晰感知上游差异，一旦建立工作树后该指示便突然消失，破坏了视觉与信息一致性。

此外，针对工作树的未提交变更（dirty）状态，若在每次打开分支菜单时主动探测所有工作树的 `git status`，会导致弹窗伴随大量并发子进程开销（特别是在 Windows 平台），破坏菜单秒开的轻量交互体验。

## Proposal

1. **工作树行数据补齐**：在 `BranchChip` 构造工作树行的阶段，依据工作树绑定的本地分支名在 `branches` 列表中检索其 `ahead`/`behind` 计数，并透明带入 `BranchRow` 模型中。
2. **工作树行渲染补齐**：在 `BranchMenu` 的 `renderFlatLeaf` 中调用既有的 `renderArrows(row)`，以一致的样式展示 `↑N` 和 `↓N`。
3. **试行评估机制**：在决策实施并落地到界面后，保持对实际体验的观察；若后续发现工作树行空间拥挤或与跳转场景关注点冲突，通过新决策直接废弃或调整该指示。
4. **维持轻量菜单原则（不引入即时 Dirty 探测）**：分支菜单仅依赖 `status` 路由已有事实；每个工作树物理目录的脏文件检查（`dirty`）严格收敛在「删除确认弹窗」以及「全量工作树管理模态框」中按需探测，不将耗时的 status 探测扩散至日常高频打开的输入框下拉菜单。

## Alternatives considered

- **下拉菜单打开时并发探测所有工作树的 Dirty 状态** —— Windows 下每次 `git status` 均为独立进程生成，工作树数量较多时会显著拖慢菜单弹出的帧率与流畅度，且大多数跳转换区分支场景并不需要立刻审视未提交细节。
- **工作树行完全不显示 `↑↓` 箭头** —— 数据早已由后端的单次 `git for-each-ref` 廉价解析出来，刻意隐藏使得用户必须切回普通分支视图才能确认是否需要更新，体验割裂。
- **直接作为永久规则而不设评估窗口** —— 工作树行具有专属的交互特征（点击跳转、物理路径 tooltip、右键管理等），其视觉密度需经过真实编码会话检验，保留试行评估更为审慎。

## Acceptance criteria

1. 在 `buildBranchRows` 和 `buildLinkedWorktreeRows` 中，工作树条目能正确继承对应同名本地分支的 `ahead` 与 `behind` 属性。
2. 在分支菜单的「工作树」分组中，具有领先或落后 upstream 提交的工作树行，其右侧正常渲染 `↑N` / `↓N` 标记及悬停提示文案。
3. 主工作树行在 linked worktree 会话中展示时，同样正确反映主分支的 `ahead`/`behind` 状态。
4. 整个分支菜单的弹出过程不新增任何额外的 Git 探测请求，保持零开销秒开。
5. 相关的单测扩展覆盖工作树行 upstream 计数继承的边界情况。

## Risks

- **工作树未配置 upstream**：无 tracking 分支的工作树行不会展示箭头（与本地分支表现一致，为预期行为）。
- **视觉密度增加**：分支名称过长加上箭头指示可能挤压右侧区域，需确保 CSS 截断规则与弹性盒布局在窄屏下表现稳定。
